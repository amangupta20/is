## 1. Standing workflow (not a task list)

**We work as one continuous technical partnership.** The loop for every slice:

1. **Orient** — read progress, architecture checkpoint, newest plan, git state. State proven vs pending before asking the user to touch Dokploy/Open WebUI.
2. **Decide the smallest useful slice** — explain in plain language: user-visible behavior, what runs automatically, what needs a model tool call, where data is persisted, effect on provider cache/context size, what native Open WebUI already does, what is explicitly deferred. Prefer external Assistant Core + Functions/Tools/MCP over forking Open WebUI.
3. **Implement locally** — one small reversible commit, keep user’s unstaged changes (especially `.gitignore`), add *one* happy-path test + *at most* one fail-open test **only if you can’t live without it**. This is an experimental 1–2 user system — no enterprise test ceremony, no 20-question interrogations.
4. **Explain** — *What changed / Why this way / What it doesn’t do yet / Verification* — without being asked.
5. **Let the user deploy** — Dokploy auto-deploys pushed `origin/assistant-foundation`. Don’t ask for routine branch/redeploy proofs; only inspect Dokploy logs/migrations when config changed or live behavior disagrees with pushed code. Give **one exact Dokploy step** with *what success looks like* and *what redacted evidence to send*.
6. **Let the user update Open WebUI** — name exact adapter files to re-import, which Valves are secret/non-secret, where Filter/Tool is attached, whether a new chat is needed. One UI group at a time.
7. **Controlled live scenario** — exact messages to send, why each tests a boundary, what API/worker/DB/UI behavior to expect, what redacted evidence to return.
8. **Evaluate usefulness, not just correctness** — Did it help? Too chatty? Too quiet? Cache hit? Latency? Choose next slice from observed pain, not from a checklist.
9. **Record continuity** — update `progress.md`, plans, and this handoff with commit range, verification, deployment and live evidence before context crowds.

**Asking:** Instead of 20 granular interrogations, use **up to 5 scenario-based options** (e.g., “Inspectability vs Files vs Memory manager vs History vs Stay lean”) and let the user pick or blend. Questions only when the answer materially changes behavior.

## 2. Division of responsibility

**Agent does:** inspect/explain repo, research Open WebUI alternatives before building, make reasonable explicit assumptions, modify repo after approval, keep small commits, run proportionate `ruff`/`mypy` (full `pytest` only when it adds signal), use `Luna/high` as read-only reviewer, explain changes, prepare exact Dokploy/Open WebUI steps, diagnose redacted logs, maintain `progress.md`/plans/handoff.

**User does:** change Dokploy env/networking, inspect redacted Dokploy logs, import/update Open WebUI Functions/Filters/Tools, set Valves/permissions, run live chat scenarios, run supplied read-only SQL via Supabase when needed.

**Agent must not:** operate Dokploy/Open WebUI via browser/API, change live secrets, request full `.env`/DB URL/HMAC, treat a `git commit` as proof of deployment, move to next gate without interpreted evidence, or start a future feature just because code compiled.

## 3. Architecture and product preferences (stable)

* Experimental personal assistant, 1 trusted primary user, possibly one bounded family user later — no hostile multi-tenant hardening.
* External-first; Open WebUI stays unforked. Use signed Filter/Tool/Event, worker, PostgreSQL, Dokploy Compose.
* Personal memory/chats/files first for personal questions; aggressive web search for informational questions.
* Stable small frozen `<user_profile>` per chat + additive tool-callable retrieval — preserves provider prefix-cache. New chat = context reset; no epoch/drop-all machinery.
* Aggressive but inspectable retrieval: compact previews first, then exact evidence/full source/neighbor expansion.
* All Library files eventually discoverable without re-attach, content-SHA-256 dedup per-user, progressive bounded read.
* Preserve raw chat/file provenance for neighbor/full-source expansion.
* Future cleanup is interactive and auditable — never silently delete inferred data.
* Keep ceremony proportionate to a personal system.
